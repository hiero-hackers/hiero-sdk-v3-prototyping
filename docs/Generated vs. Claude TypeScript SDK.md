# Generated vs. Claude: TypeScript and Java SDK

This file compares six versions of the same base types (`Page`, `NativeTokenUnit`, `NativeToken`, `ExchangeRate`,
`Network`, `BaseAddress`, `Address`, `ZERO_ADDRESS`, `EvmAddress`):

| Short name | What it is | Where |
| --- | --- | --- |
| **TS generated** | TypeScript API generated by metalang from the current specs; method bodies are stubs | `sdk-ts/generated/packages/base` on branch `deterministic-generator` (git-ignored) |
| **Java generated** | Java API generated by metalang from the same specs; method bodies are stubs | `sdk-java/generated/org.hiero.base` (git-ignored) |
| **Java impl** | The Java SDK: a copy of Java generated with every stub filled in by hand | `sdk-java/impl/org.hiero.base` (tracked) |
| **Claude TS** | Hand-written TypeScript implementation Claude wrote from four OpenSpec deltas | commit `fc3737a3`, branch `claude-ts-implementation`, `sdk-ts/hiero-sdk-base-api` |
| **Codex Java** | Hand-written Java API Codex wrote from six OpenSpec deltas; implemented changes 1-4 only | PR #31, `feat/java-base-public-api-openai` (`45779e4e`), `sdk-java/hiero-sdk-base-api` |
| **Claude Java** | Hand-written Java API Claude wrote from the same six deltas; implemented all six | PR #32, `feat/java-base-public-api-claude` (`1da79859`), `sdk-java/hiero-sdk-base-api` |

The TypeScript versions are compared in the first sections, and the Java PRs against Java generated and Java impl in
[Java: Codex and Claude PRs against generated and impl](#java-codex-and-claude-prs-against-generated-and-impl).
`Codex vs. Claude Java SDK.md` compares the two PRs with each other.

**Java impl is what Claude TS was trying to be, built on the current specs.** Both generated trees are the API
surface only: their behavior methods throw `Not implemented yet`. Java impl fills those stubs and follows every
behavior rule of the current specs. Claude TS fills the same behavior, but it was written against an older, narrower
spec: it agrees with the current spec on six decisions and contradicts it on four. In all four cases Java impl
already does what the spec asks.

| Aspect | TS generated | Java generated | Java impl | Claude TS |

| int64 / uint64 | `bigint` + range checks | `long` (uint64 kept as `long`, per the Java guide) | `long`; unsigned printing via `Long.toUnsignedString` | `bigint` + range checks |
| Errors | `RangeError`, `TypeError`, `PaginationError` | `IllegalArgumentException`, `NullPointerException`, `PaginationException` | Same as Java generated | `RangeError`, `TypeError`, `IllegalFormatError`, `MirrorNodeError` |

## Where the specs now decide what Claude chose

The OpenSpec deltas left these questions open; Claude TS answered them (with your choices at the time). The current
specs answer them in behavior rules and method comments, and the generators turn those into tests. Both generated
trees only declare the behavior, so they are not listed here.

| Question | Current spec | Java impl | Claude TS |
| --- | --- | --- | --- |
| `to()` with an inexact result | Fails: “a conversion never loses a part of the amount” | `IllegalArgumentException` | `RangeError` ✓ |
| `to()` result outside int64 | Fails | `IllegalArgumentException` (`longValueExact`) | `RangeError` ✓ |
| `toBaseUnits()` result outside int64 | Fails (`invalid-argument-error`) | `IllegalArgumentException` | **Unbounded `bigint`** ✗ |
| `validateChecksum()` with no checksum | `true` (`rule:checksum-validation`) | `true` | **`false`** ✗ |
| Checksum algorithm | HIP-15 over `Network.id` | HIP-15 (`EntityIds.checksum`, `long` arithmetic) | HIP-15 (`number` arithmetic) ✓ |
| Text form of `fromString()` | Canonical HIP-15: no leading zeros, whitespace or sign; five lowercase checksum letters | Canonical (`EntityIds.parse`) | Canonical ✓ |
| Parsing validates the checksum | Never | Never | Never ✓ |
| Error for a malformed string | `illegal-format` → `RangeError` (TS) / `IllegalArgumentException` (Java) | `IllegalArgumentException` | **`IllegalFormatError extends Error`** ✗ |
| Error of page navigation | `pagination-error` | `PaginationException` | **`MirrorNodeError`** ✗ |

✓ agrees with the current spec · ✗ contradicts it.

One Java impl detail: `EntityIds.parse` reads numbers with `Long.parseLong`, so a text id with a part above
`Long.MAX_VALUE` (up to 2^64 − 1 is a valid uint64) is rejected, although such an id can be built and printed.
Claude TS parses the full uint64 range.

## Per type

### `Page<T>` and its error

| | TS generated | Java generated / impl | Claude TS |
| --- | --- | --- | --- |
| Shape | `interface Page<T>` | `abstract class Page<T>` | `abstract class Page<T>` |
| `data` | `readonly data: ReadonlyArray<T>` | `List.copyOf(data)` in the constructor, `data()` accessor | Frozen copy, `ReadonlyArray<T>` |
| `size`, `pageIndex` | `number`, unchecked | `int` (the type is the range) | `number`, checked as int32 |
| Navigation | `Promise<Page<T>>` | `CompletionStage<Page<T>>` | `Promise<Page<T>>` |
| Error | `PaginationError` (`ErrorOptions`) | `PaginationException(message, cause)` | `MirrorNodeError` (`ErrorOptions`) |

Java and Claude TS reached the same design independently: an abstract class that snapshots the data once for every
implementation. The TS generator chose an interface, so each mirror node page implementation has to copy and freeze
the data itself.

### `NativeTokenUnit` and `NativeToken`

| | TS generated | Java generated | Java impl | Claude TS |
| --- | --- | --- | --- | --- |
| Unit | `interface`, `baseUnitFactor: bigint` | `interface`, `long baseUnitFactor()` | Same; `HbarUnit` implements it | `abstract class`, factor validated > 0 and int64 |
| Token | `interface NativeToken<Self, Unit>` | `abstract class` holding `amount`/`unit`; `to()` and `toBaseUnits()` abstract | Same | `abstract class` with shared `to()`/`toBaseUnits()` and a `protected abstract create()` hook |
| Where conversion lives | Per token (`Hbar`, stub) | Per token (`Hbar`, stub) | In `Hbar`, with `BigInteger` and `divideAndRemainder` | Once, in the base class |
| Concrete token | `Hbar` in `hedera` | `Hbar` in `hedera` | `Hbar` + `toTinybars()`, `equals` by exact tinybars | None (deferred) |
| Mixing units of two tokens | Not prevented (structural) | Prevented: `Unit` is nominal in Java | Prevented | Prevented when units declare a private brand |

Java impl puts the exact-conversion logic in `Hbar`, so every future network token re-implements it. Claude TS's
template method (`create()`) puts it in the base class once; that is the one design point where Claude TS is ahead
of both generated APIs.

### `Network<Unit>`

| | TS generated | Java generated / impl | Claude TS |
| --- | --- | --- | --- |
| Shape | `class` with private fields | `record Network<Unit>(byte[] id, @Nullable String name, Unit nativeTokenUnit)` | `class` with private fields |
| `id` copying | In and out | In (compact constructor) and out (`id()` returns a clone) | In and out |
| `name` absent | `undefined` accepted, stored as `null` | `null` (`@Nullable`) | Only `null`; `undefined` is a `TypeError` |
| Unit check | Not null | Not null | `instanceof NativeTokenUnit` |
| Equality | None | `equals`/`hashCode` with `Arrays.equals` on `id` | None |

### `BaseAddress`, `Address` and `ZERO_ADDRESS`

| | TS generated | Java generated | Java impl | Claude TS |
| --- | --- | --- | --- | --- |
| `BaseAddress` | `interface` | `abstract class` storing `shard`, `realm`, `checksum`, `@Nullable Long num`; methods abstract | Same | `abstract class`; `num` abstract, `toStringWithChecksum()` shared |
| `Address` constructor | `new Address({ shard, realm, checksum, num })` | `new Address(shard, realm, checksum, num)` | Same | Private; `Address.of(shard, realm, num, checksum = "")` |
| Narrowed `num` | Getter `num: bigint` | `Long num()` override | Same | Getter `num: bigint` |
| Checksum format at construction | Not checked | Not checked | Not checked | `""` or five lowercase letters |
| `fromString`, `toString`, `toStringWithChecksum`, `validateChecksum` | Stubs | Stubs | Implemented in `ledger/internal/EntityIds` (shared with `AccountId`, `ContractId`) | Implemented in `address.ts` + internal `checksum.ts` |
| Equality | None | `equals`/`hashCode` on all four fields (generated) | Same | None |
| `ZERO_ADDRESS` | `constants.ts`, next to `ZERO_ACCOUNT_ID`, `ZERO_CONTRACT_ID` | `LedgerConstants` | `LedgerConstants` | `address.ts` |

Neither generated API, nor Java impl, checks the checksum format when an `Address` is constructed directly, so
`new Address(0, 0, "ABC", 1L)` prints `0.0.1-ABC`, which `fromString` then rejects. Claude TS rejects it at
construction.

### Against today's behavior rules

Claude TS is compared with the rules above; here are the same rules for the Java PRs. Codex Java has no
address code, so only the non-address rules apply to it, and none of them is decided by code it contains.

| Rule | Java impl | Claude Java |
| --- | --- | --- |
| Empty checksum, `rule:checksum-validation` → `true` | `true` | **`false`** ✗ |
| HIP-15 checksum over `Network.id` | ✓ | ✓ (`0.0.123` → `vfmkw` on ledger `00`) |
| Canonical text form, `rule:entity-id-text-form` | ✓ | ✓ |
| uint64 parts above `Long.MAX_VALUE` in text | **Rejected** (`Long.parseLong`) | Accepted (`Long.parseUnsignedLong`) ✓ |
| `EvmAddress.fromString` in mixed case that is not EIP-55 | Rejected | **Accepted** ✗ |
| `illegal-format` → `IllegalArgumentException` | ✓ | ✓ |
| `pagination-error` → `PaginationException` | ✓ | **`MirrorNodeException`** ✗ (Codex too) |
| `ExchangeRate` as a record with `isExpiredAt(time)` | ✗ (not brought up to date yet) | ✗ (Codex too) |

✓ agrees with the current spec · ✗ contradicts it.

Claude Java gets the empty checksum wrong in the same way as Claude TS. It is right where Java impl is wrong: it
parses the full uint64 range.

### What carries over to Java impl

- **The uint64 parsing of Claude Java.** `Long.parseUnsignedLong` in `EntityIds.parse` closes the gap that impl
  rejects valid ids above `Long.MAX_VALUE`.
- **Nothing else from the code.** Impl already has the rest, built on the current specs, and gets Keccak-256 from
  BouncyCastle, so Claude's hand-written `Keccak256` is not needed.
- **From Codex, the build setup:** doclint with `failOnWarnings`, a CycloneDX SBOM and pinned plugin versions. The
  same is worth checking for `sdk-java/impl`.
- **`ExchangeRate` is behind in every hand-written Java version.** Impl and both PRs still have the abstract class
  with a `double` rate, which the current spec replaced with a record of whole numbers.

## What this means

1. **Java impl is the template for a TypeScript impl.** It shows the intended workflow: copy the generated project
   once, fill the stubs by hand, keep helpers in non-exported `internal` packages. TypeScript has no such module yet,
   and how spec changes reach an impl is still undecided (CLAUDE.md). That decision comes before any porting.
2. **Claude TS is a good source for the TypeScript stubs.** Its HIP-15 checksum, canonical parser, exact `to()` and
   range helpers implement rules the current spec states almost word for word. Port them with the four fixes Java impl
   already has: empty checksum → `true`, `toBaseUnits()` overflow throws, malformed text → `RangeError`, and
   `MirrorNodeError` → `PaginationError`.
3. **The shape must follow the TS generator.** Interfaces for abstractions, `init`-object constructors and subpath
   exports are the TS guideline's mapping; Claude TS's abstract classes, `Address.of()` and branded units would have
   to be proposed as guideline changes to survive. That Java's generator keeps `Page`, `NativeToken` and `BaseAddress`
   as abstract classes is a fair argument for such a proposal.
4. **Three questions worth raising in the specs or guidelines:**
   - No version checks the checksum format of a directly constructed `Address` (TS generated, Java generated,
     Java impl).
   - Java impl cannot parse uint64 text above `Long.MAX_VALUE`.
   - TS generated accepts `undefined` for `Network.name`, although `api-best-practices-js.md` says `undefined` is never
     accepted.
5. **The Java PRs confirm the pattern.** Claude Java makes the same empty-checksum mistake as Claude TS and fixes the
   uint64 gap of Java impl. Codex Java is a strict, well-tested copy of the API surface that the generator already
   produces. Neither PR adds a type or decision that Java generated and Java impl lack, apart from the uint64 parsing.
