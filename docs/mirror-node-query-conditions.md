# How the Mirror Node evaluates query conditions

> **Status:** analysis, input for the design of typed query conditions in `spec/mirror-node-client` (Phase 2 of the
> REST coverage, see [missing-features.md](missing-features.md) §4). Measured on 2026-11-02 against the public Hedera
> **mainnet** and **testnet** Mirror Nodes, both version **0.165.1**; the pinned OpenAPI definition
> (`tooling/openapi/mirror-node/openapi.yml`) is **0.164.0**. Raw results:
> [mainnet](mirror-node-query-conditions-results-mainnet.md), [testnet](mirror-node-query-conditions-results-testnet.md),
> generated by [`tooling/openapi/probe-mirror-node-conditions.py`](../tooling/openapi/probe-mirror-node-conditions.py).

## Why

Many query parameters of the Mirror Node REST API take conditions: `account.id=gte:0.0.5`, repeatable
(`timestamp=gte:1700000000&timestamp=lt:1700003600`). The OpenAPI definition describes them only by a regular
expression per parameter, which says nothing about how repeated conditions combine, which combinations are rejected,
or what happens with contradictions. The V3 specs model the conditions as `list<string>` in REST syntax for now; a
typed model can only be designed on what the server really does.

## Method

The probe script takes every query parameter with conditions from the pinned OpenAPI definition (61 parameters on
33 endpoints, plus 4 documented without conditions but suspected to accept them, plus 3 with a required companion
parameter) and sends each one:

- **23 variants**: the bare value, each of the six operators, two `eq`, two bare values, the same `eq` twice, two `ne`,
  inclusive and exclusive ranges, a point range, redundant lower and upper bounds, two `gte`, a contradictory range
  (`gt:hi&lt:lo`), an empty range (`gt:x&lt:x`), and the combinations `eq`+range, `eq`+`ne`, range+`ne` and all at once;
- **boundary values** of the value type (formats, lengths, signs, empty values, unknown or upper-case operators) and
  **100 / 101 conditions** for one parameter;
- **general checks**: `limit`, `order`, repeated and unknown parameters, conditions across pages, two parameters at
  once, and `/tokens?account.id=X` against the token relationships of X.

The path parameters (accounts with airdrops, allowances, NFTs, rewards; contracts, topics, tokens) are found by the
script among the busiest entities of recent transactions, so each network contributes what it has data for: an NFT
with a long history among the NFTs of recent transfers, an account whose NFTs have several spenders among the accounts
that approved allowances. The
sample values `lo < mid < hi` come from the unfiltered first page (`limit=100`) of the same endpoint, so they exist;
for `spender.id` of `/accounts/{id}/nfts` from the NFTs that have a spender (`spender.id=gte:0.0.1`), because they are
rare in the unfiltered list.
A variant is checked against the returned items: every item must satisfy the conditions, and if the answer has no
further page, every matching item of the unfiltered page must be in it. Repeated `eq` values are checked under both
readings, IN (any of them) and AND (all of them), and for "only the first / last one applied". `/transactions`
`account.id` is checked against the accounts of the transfers and the payer (an item matches if one of them does).
About 5,000 read-only requests over both networks; the conspicuous cells were re-checked by hand.

Both networks gave the same behaviour wherever both had data; differences in the raw results come from data
(a fixture with too few values, balances that changed between two requests).

## Findings

### 1. There is no uniform behaviour; seven families

| Family | Parameters | Operators | Repeated conditions |
|---|---|---|---|
| **A. Free** | `/accounts` `account.id`, `account.balance`; `/accounts/{id}` `timestamp` (its transactions); `/balances` `account.id`, `account.balance`; `/contracts` `contract.id`; `/contracts[/{id}]/results` `timestamp`; `/schedules` `schedule.id`, `account.id`; `/tokens` `token.id`; `/tokens/{id}/balances` `account.id`, `account.balance`; `/tokens/{id}/nfts` `account.id`, `serialnumber`; `/tokens/{id}/nfts/{serial}/transactions` `timestamp`; `/transactions` `timestamp` | all six | any number (up to 100), all combined with AND, except repeated `eq` (see 2) |
| **B. Free without `ne`** | `/accounts/{id}/tokens` `token.id`; `/accounts/{id}/allowances/crypto` `spender.id`; `/accounts/{id}/rewards` `timestamp`; `/contracts/{id}/state` `slot`, `timestamp`; `/blocks` `block.number`; `/topics/{id}/messages` `timestamp`, `sequencenumber`; `/contracts/results/{id}/actions` `index` | eq gt gte lt lte; `ne` → 400 | as A |
| **C. One of each** | `/accounts/{id}/nfts` `token.id`, `serialnumber`, `spender.id`; `/accounts/{id}/allowances/tokens` `spender.id`, `token.id`; `/accounts/{id}/allowances/nfts` `account.id`, `token.id`; `/contracts[/{id}]/results/logs` `timestamp`, `index` | eq gt gte lt lte; `ne` → 400 | at most one `eq`, one lower and one upper bound ("Only one gt/gte operator is allowed"); otherwise 400. Exception: `spender.id` of `/accounts/{id}/nfts` accepts any number of `eq` (IN) and rejects only a second bound ("Multiple range params not allowed") |
| **D. One `eq` wins, `ne` ignored** | `/accounts/{id}/airdrops/outstanding` `receiver.id`, `token.id`, `serialnumber`; `/accounts/{id}/airdrops/pending` `sender.id`, `token.id`, `serialnumber` | eq gt gte lt lte; **`ne` → 200 without effect** | **of several `eq` only one is applied** - the lexicographically last, whatever their order in the URL; redundant bounds are applied together; `eq` with a bound or `ne`, and the range + `ne` → 400 |
| **E. `ne` ignored** | `/network/nodes` `node.id`; `/network/registered-nodes` `registerednode.id`; `/transactions` `account.id` | eq gt gte lt lte; **`ne` → 200 without effect** | `node.id`, `account.id`: as A; `registerednode.id`: two different `eq` → 400 |
| **F. Equality only** | `/contracts[/{id}]/results` `block.number`, `block.hash`, `transaction.index`; `/contracts/results/logs` `transaction.hash`; `/network/nodes` `file.id` | `eq` only, every other → 400 | `transaction.hash`, `file.id`: one value; the others accept repeated `eq` |
| **G. Point in time** | `timestamp` of `/contracts/{id}`, `/tokens/{id}`, `/network/exchangerate`, `/network/fees`, `/network/supply`, `/balances`, `/tokens/{id}/balances` | varies: `/tokens/{id}` only eq lt lte; `/network/*` gt/gte → 404, `ne` → 400 | selects one state, not a set of items |

`/tokens` `account.id` fits no family: it accepts only a bare value — every operator and every repetition is
rejected — and then returns exactly the tokens the account has a relationship with (checked against
`/accounts/{id}/tokens`).

### 2. Repeated `eq` means IN, AND or "only one", depending on the parameter

| Repeated `eq` | Parameters |
|---|---|
| **IN** (any of the values) | `account.id` (`/accounts`, `/balances`, `/transactions`), `contract.id`, `token.id` (`/tokens`, `/accounts/{id}/tokens`), `spender.id` (allowances/crypto, `/accounts/{id}/nfts`), `slot`, `timestamp` of `/contracts[/{id}]/results` and `/accounts/{id}/rewards`, `node.id` |
| **AND** (all of the values; two different values give nothing) | `account.balance`, `schedule.id`, `account.id` of `/schedules`, `/tokens/{id}/balances` and `/tokens/{id}/nfts`, `timestamp` of `/transactions`, `/accounts/{id}`, `/tokens/{id}/nfts/{serial}/transactions` and `/topics/{id}/messages`, `sequencenumber`, `block.number` (`/blocks`), `serialnumber` (`/tokens/{id}/nfts`), `index` (actions) |
| **only one** (the lexicographically last, independent of the order in the URL) | all airdrop parameters (family D) |
| **rejected** (400) | family C (except `spender.id` of `/accounts/{id}/nfts`), `registerednode.id`, `transaction.hash`, `file.id` |

The same kind of value behaves differently: `timestamp` is IN on `/contracts/results` and AND on `/transactions`;
`account.id` is IN on `/accounts` and AND on `/schedules`.

### 3. Contradictions give an empty result — with exceptions

A contradictory (`gt:hi&lt:lo`) or empty (`gt:x&lt:x`) range, `eq` outside the range and `eq:x&ne:x` return 200 with
no items in families A and B, and for `token.id` and `serialnumber` of the airdrops. The exceptions:

- **`/contracts/results/logs` `timestamp` ignores a contradictory or empty range** and returns unfiltered items
  (verified by hand: `gt:<newest>&lt:<oldest>` returns the newest logs);
- `node.id`, `registerednode.id`, `receiver.id` / `sender.id` of the airdrops and `/accounts/{id}/allowances/nfts`
  reject it with 400;
- `/accounts/{id}` answers 404 ("Timestamp range is empty").

Redundant bounds (`gt:lo&gte:mid`, `lt:hi&lte:mid`, `gte:lo&gte:mid`) are applied together — the stricter bound
wins — in families A, B and D, and rejected with 400 in family C.

### 4. Limits, values and load

- **100 conditions per parameter**: 100 are accepted, 101 are rejected ("Array limit exceeded. Only 100 elements
  allowed in an array"); counted over all operators of the parameter. Measured with `ne`, so only on the parameters
  that support `ne`; elsewhere the 400 comes from the operator.
- **Load:** on mainnet, several `eq` values for `account.balance` on `/accounts` do not finish: 502 / 503 or a timeout
  after 30 s, where one value or a range answers in 0.7 s. Two `eq` with `ne` on `/transactions` `account.id` gave a
  503 on testnet once.
- **`limit`** must be 1 or more; **more than 100 is accepted and silently capped at 100** (`limit=1000` → 100 items),
  although the OpenAPI definition says at most 100. `limit` and `order` must not be repeated (400); `order` is not
  case-sensitive.
- **Entity ids**: `5`, `0.5` and `0.0.5` are the same; a leading zero (`0.0.05`) and 11 digits are accepted; a
  checksum (`0.0.5-vfmkw`), a negative number, an empty value, an upper-case or unknown operator and a leading space
  are rejected. The airdrop endpoints and `/accounts/{id}/allowances/nfts` are more lenient: they accept an empty
  value, an upper-case operator (`EQ:`) and a leading space; `/network/nodes` `file.id` accepts the first two.
  An EVM address is accepted for the account parameters (`account.id` of `/accounts`, `/balances`, `/transactions`,
  `/schedules`, `/tokens`, `spender.id` of the allowances), but rejected for `contract.id`, on the airdrop endpoints
  and on `/accounts/{id}/allowances/nfts`.
- **Timestamps**: seconds with 0 to 9 decimal digits; 10 decimal digits, 11-digit seconds, negative values, exponents
  and ISO 8601 are rejected.
- **Integers**: `serialnumber` (NFTs) and `sequencenumber` reject 0, but on the airdrop endpoints an airdrop of a
  fungible token counts as serial number 0 (`serialnumber=eq:0` returns exactly the fungible ones, `lt:200` includes
  them); values above int64 are rejected with 400 — but `index` (`/contracts/.../logs`,
  `/contracts/results/{id}/actions`) and `transaction.index` answer **503 Service unavailable** for int64 max,
  int64 max + 1, 20 digits and a decimal.
- An empty value means "no condition" on `/network/nodes` (`node.id=`, `file.id=`), `/network/registered-nodes` and
  `/network/exchangerate`.

### 5. Dependencies between parameters

- `serialnumber` on `/accounts/{id}/nfts` needs `token.id` ("serialnumber without a token.id parameter filter");
  `token.id` on `/accounts/{id}/allowances/tokens` needs `spender.id`; `token.id` on `/accounts/{id}/allowances/nfts`
  needs `account.id`; `index` on the logs endpoints needs a `timestamp`; `transaction.index` needs `block.number`.
- Conditions on two parameters are combined with AND (`account.id` range + `account.balance=gt:0`).
- Conditions survive pagination: the `next` link keeps all conditions and adds its own cursor condition
  (`account.id=gt:0.0.6`); range + two `ne` with `limit=2` gave exactly the expected 16 accounts over 8 pages.
- Single-object endpoints (`/contracts/{id}`, `/tokens/{id}`) reject unknown query parameters (`limit`), list endpoints
  such as `/network/nodes` ignore them.

### 6. Where the OpenAPI definition is wrong

| Parameter | OpenAPI | Server |
|---|---|---|
| `/tokens` `account.id` | all operators | no operator at all |
| `node.id`, `registerednode.id` | no `ne` | `ne` accepted and **ignored** |
| airdrop parameters, `/transactions` `account.id` | `ne` (airdrops: not for `serialnumber`) | `ne` accepted and **ignored** |
| `/balances` `account.id` | no operators | all six |
| `sequencenumber`, `transaction.index` | plain integer | `sequencenumber`: eq gt gte lt lte; `transaction.index`: `eq` |
| `limit` | 1 – 100 | above 100 capped |
| `serialnumber` | `\d{1,19}`, also 0 | 0 rejected (NFTs); 0 = fungible (airdrops) |
| family C, `file.id`, `transaction.hash` | repeatable | at most one per operator / one value |

### 7. Causes in the source code

Read in the mirror node source at tag `v0.165.1` (commit `6a7a3f5`). The REST API has two implementations: most
endpoints are served by the Node.js module `rest`, a growing part by the Java module `rest-java` (allowances of NFTs,
airdrops, hooks, `/network/nodes`, `/network/registered-nodes`, `/network/exchangerate`, `/fees`, `/supply`, `/stake`,
`/topics/{id}`). The Java module replaces the Node.js one endpoint by endpoint (`docs/checklist/rest-conversion.md`
of the mirror node: implement in Java, then enable the route per network, then delete the JavaScript code); an ingress
sends the converted paths to `rest-java`, everything else to `rest`. Each endpoint parses its conditions by hand;
there is no shared contract.

| Behaviour | Cause | Intended? |
|---|---|---|
| Family C (one `eq`, one lower, one upper bound) | `rest/controllers/bound.js`: "Holds the filters for query parameters in a multi-column paging query"; the endpoints are paged over two columns (`token.id` + `serialnumber`, `spender.id` + `token.id`, `timestamp` + `index`, `account.id` + `token.id`) | yes, a simplification of keyset paging over two columns |
| `spender.id` of `/accounts/{id}/nfts` deviates from C | not a paging column; own check in `rest/controllers/accountController.js` (`validateFilters`) | yes |
| Repeated `eq`: IN or AND | `parseParams` in `rest/utils.js` collects `eq` values into `IN` only when the caller passes `allowMultiple` (`account.id`: yes, `account.balance`, `timestamp`: no); otherwise every `eq` becomes its own `and` clause | the IN is; the AND of different values is a side effect - it can never match and is not rejected |
| Family B (no `ne`) | explicit `throw` per controller (`topicmessage.js`, `cryptoAllowanceController.js`, `tokenController.js`, ...) | yes, the reason is not documented |
| Airdrops: one `eq` wins, `ne` ignored | `rest-java/.../service/Bound.java`: every `eq`/`gt`/`gte` overwrites `lower`, `ne` is only counted; the NFT allowances use the same class but call `verifyUnsupported(NE)` and `verifySingleOccurrence()`, `TokenAirdropsController` does not | no, a missing validation |
| `node.id`, `registerednode.id`: `ne` ignored | the loops in `rest-java/.../service/NetworkServiceImpl.java` have no branch for `ne` | no, a missing validation |
| `/transactions` `account.id=ne:X` without effect | `transactions.js` applies `ne` to each transfer row (`ctl.entity_id != X`), so it matches every transaction with a transfer to any other account - nearly all | not ignored but per transfer; as an exclusion of an account useless |
| `/contracts/results/logs`: contradictory or empty `timestamp` range ignored | `optimizeTimestampFilters` in `rest/controllers/contractController.js` returns no filters at all when the range is empty; only used without a contract id | no |
| Upper-case operators, empty values accepted | `rest-java/.../common/RangeOperator.of` upper-cases the operator; `rest` does not | no, an implementation difference |

## Not covered

- **Hook storage** (`/accounts/{id}/hooks/{hookId}/storage` `key`, `timestamp`): the hook endpoints are not enabled
  on either network - they are served by `rest-java` behind the route switch `routes.hooks`, which defaults to `false`
  (`charts/hedera-mirror-rest-java/values.yaml`), and answer 404 "Not found" like an unknown path; there is also no
  `HOOKSTORE` transaction yet. The source (`HooksController`, `Bound.of` for `timestamp`) suggests the airdrop
  pattern of section 7. The typed conditions are designed without them; if the behaviour is still
  unknown when they are specified, the filtered `getHookStorage` overload is left out at first and added once the
  conditions are verified.
- **`file.id`** of `/network/nodes`: there is only one address book file per network, so only the status was checked.
- `/tokens/{id}/nfts/{serial}/transactions` `timestamp` was checked on mainnet only: among the NFTs transferred
  recently on testnet none had enough transactions.
- **Semantics not checkable**, because the value is not part of the returned items: `/blocks` `timestamp`, the
  point-in-time timestamps (family G), the equality-only parameters of contract results (the list items carry no
  block).
- One server version (0.165.1, one minor above the pinned definition). The probe is repeatable:
  `python3 -I tooling/openapi/probe-mirror-node-conditions.py [--base <mirror node>/api/v1] --markdown <file>`.

## Consequences for the typed conditions

These are inputs for the design, not decisions:

- A **single generic condition type with all six operators** would let callers build requests that are rejected
  (families C, F), ignored (`ne` in D and E) or silently mean something else (IN, AND, one `eq`). The operator set and
  the meaning of repeated values belong to the **parameter**, not to the value type.
- What remains meaningful everywhere is small: **one value, a set of values (only where it is IN), at most one lower and
  one upper bound, and exclusions (only in family A)**. Redundant and contradictory
  bounds never add expressiveness.
- Where repeated `eq` means AND or "only one", a set of values is useless or dangerous; such parameters need a
  single value, not a set.
- Point-in-time timestamps (family G) are not conditions on items but the selection of a state; they deserve their own
  shape (`at` / `before`).
- Server faults the SDK should guard against or document: `ne` ignored (D, E), only one `eq` applied (D),
  contradictory range ignored on `/contracts/results/logs`, 503 for large `index` values, several `account.balance`
  values not finishing on mainnet, `limit` above 100 capped.
