How to read every diagram on this page

This repository has three kinds of part, and the difference decides whether you may edit a file. Each diagram draws them the same way: colour says who owns it, a dashed outline says it is not ours at all.

generated

Written by metalang from the specs and the TCK bindings. Every file carries a header line, none is edited by hand, and files the generator stops producing it deletes.

hand-written

Maintained by people and holding no generated file: the specs themselves, the generator, the support types, the TCK bindings and the TCK runtimes.

outside this repository

The cloned TCK and the network under test. We never change these — we satisfy them, and a dashed edge marks every crossing into them.

01The generation pipeline

The specs in spec/ are written in a meta-language, not in any target language. One parser builds one model; three generators turn that model into three idiomatic projects.

Everything downstream hangs off metalang-core: it parses the fenced ## API Schema blocks, validates them against the rule catalogue, and links the result into a model where every type reference is resolved. The per-language modules never see Markdown — they see that model, plus the one file that holds the decisions a language-neutral spec cannot express.

What the configuration decides

A spec says what the API is, never how a language should package it. That lives in one generator.properties per language: Maven coordinates and which abstractions become interfaces, the npm scope, the crate prefix — and, added in this branch, which spec folders need the protobuf messages.

02Generated or hand-written, never both

ADR-0007 is the spine of the repository: a module is produced entirely by a generator or maintained entirely by hand. The colours on this page are that rule.

The point is ownership. A generated module is reproducible from versioned inputs, carries a header line on every file and is never edited; files the generator stops producing are deleted by it. Everything else is maintained by hand. When generated code needs something hand-written, the interface between them is explicit — and it comes in exactly three shapes.

The one deliberate exception. The createAccount spike edits generated/java and generated/ts in place, because the generated shapes leave no other option — AccountCreateTransaction is final with stubbed overrides, the factories are final with private constructors. Regenerating destroys it; docs/rebuilding-the-spike.md is the runbook.

03One protobuf source

Hiero has three node types with a protobuf interface, and their definitions live in three repositories. protobuf/ vendors all three at pinned versions so every generator works from one tree.

They are not independent. The consensus node is the base: services/basic_types.proto declares the shared types, the mirror node imports it directly, the block node reaches it through block/stream/. Import paths are root-relative, so each directory is one include root and the two dependants additionally need the consensus-node root on the path.

DirectoryUpstreamPinFiles
consensus-node/hiero-consensus-nodev0.77.2208
block-node/hiero-block-nodev0.44.218
mirror-node/hiero-mirror-nodev0.164.02

update.sh re-fetches from the pins and records the resolved commit; verify.sh compiles every root with protoc into a descriptor set — the language-neutral proof that every import resolves. Both protoc and the well-known types come through the repository's Maven wrapper, so no protobuf installation is needed.

Generated, and never public

All three languages generate from that tree at build time, and in none of them is the result part of the public API: the wire format changes with every network release, so exposing it would make every protocol change a breaking change of the SDK. Each language expresses that with its own mechanism.

LanguageKept internal byA foreign importer gets
Java exports … to … naming only the SDK modules package … is not visible
Rust mod proto; without pub module `proto` is private
TypeScript subpath absent from exports ERR_PACKAGE_PATH_NOT_EXPORTED

Java is the only one that needs a separate module for it: JPMS forbids a package from being split across modules, so the protobuf packages must have exactly one owner. Rust and TypeScript keep the code inside the crate resp. package that uses it. The generators own this wiring — one key per language names the spec folders that need it — so it survives a regeneration.

04How the TCK server is built

The Hiero TCK drives any SDK through a JSON-RPC server. Here that server is generated from two Markdown files.

tck/bindings/*.md declares, in fenced bindings blocks, how each TCK method maps onto the API: which parameter becomes which attribute, through which converter, and which results are read back. metalang tck generate turns that — together with the converter catalogue in the core — into a contract and a server. The parts that cannot be derived from the bindings are hand-written once per language.

Contract and server: why two generated modules

Both come out of the same metalang tck generate, and they have opposite jobs. The contract is declarations only; the server is the code that answers TCK methods. What makes the split work is that the server is never compiled against the thing that implements the contract.

java-tck/contractjava-tck/server
Holds6 interfaces, 342 lines, no method body3 classes, 283 lines, the bound TCK methods
Derived fromthe converter catalogue and the binding flowtck/bindings/*.md
Compiled againstthe SDK APIthe contract and the SDK API
Implemented bytck/runtime/java, by hand—

Converters is the clearest case: it declares exactly 20 methods, one per entry of the converter catalogue in metalang-core — string/stringJson, tinybar/tinybarJson, accountId/accountIdJson and so on. TckRuntime declares the binding flow itself: required, or, unsupported, transaction, query, put.

# generated/java-tck/server/pom.xml
hiero-sdk-tck-contract      compile
hiero-base · …-client · …     compile
hiero-sdk-tck-runtime       runtime   ← the whole point

Why not let the server call the runtime directly? It did, before ADR-0007 — by name, Converters::accountId and Params.value(…). The contract existed only in the generator’s string templates, so a renamed method or a missing converter surfaced during a TCK run at the earliest, and only for the parts the current bindings happened to use. Now a new entry in the converter catalogue changes Converters, and every runtime that has not followed stops compiling. The drift is found by the compiler, not by a test run.

TypeScript has the same pair — @hiero/tck-contract and @hiero/tck-server — with a dynamic import in place of ServiceLoader, and a server tsconfig that deliberately does not reference the runtime.

What comes from the TCK repository

The TCK is a separate project, cloned next to this one and pointed at through TCK_DIR. It is not a library this repository depends on — it is a driver that this repository has to satisfy. Four things cross that boundary, and one of them is easy to miss.

CrossingWhenDirectionWhat it fixes
docs/test-specifications/ buildin The method names, parameters and results every binding must cover. metalang tck check reports each unbound method and each parameter without a binding or an explicit unsupported.
.env runout Operator, node address, mirror node URL, server port. We write tck/solo.env into the clone; an existing file is kept as .env.before-v3.

Everything else in the clone — the mocha runner, the 64 test files, the preflight reachability check, the HTML report — is the TCK’s own business. Nothing in this repository imports from it, and the only file we write into it is .env.

Which endpoints the server must have

The same 80 files that feed tck check are the contract. Every request type gets one Markdown file in a service folder, written from TestSpecificationsTemplate.md, and each one carries a section that is the endpoint definition — not prose about it:

In the spec fileDefines
### Method NameThe exact JSON-RPC method, e.g. createAccount.
### Input ParametersA table of name, type, required or optional, and notes — key is a DER-encoded hex string, initialBalance is tinybars.
### Output ParametersA table of name, type and meaning: for createAccount, accountId and status.
## Property TestsNumbered tables of test, input and expected response, with an Implemented (Y/N) column — the tests in src/tests/ are the executable form of these rows.

Three things live in common/ because they are not tied to one request type. Utility.md specifies the methods every server must answer regardless of which transactions it supports — setup, reset and generateKey, each with its input and output parameters. CommonTransactionParameters.md specifies the commonTransactionParams object every transaction method accepts, including the signers list. ErrorCodes.md defines exactly one custom error code:

CodeMeaningWhere it comes from
-32001Hiero error: the network rejected the request at precheck or at consensus. data carries status and a message.The TCK’s own ErrorCodes.md
-32601Method not found — the honest way to say “this server does not implement that”. The suite skips those tests instead of failing them.JSON-RPC 2.0
-32603Internal error: the SDK rejected the request before it reached the network, or could not build it.JSON-RPC 2.0

That -32601 is what makes partial implementations useful: a server declares its surface by which methods it answers, and the suite adapts. Governance is in DevelopmentProcess.md — documentation first, a named lead per SDK, and the TCK change and the SDK changes merged in step.

In CI the clone disappears

hiero-tck-action is a composite GitHub Action that checks out hiero-ledger/hiero-sdk-tck itself, pinned by a tckTag input, installs it, waits for the server and runs the suite. Three of the four crossings above become inputs: no TCK_DIR, no .env copying, no npm install in a sibling directory.

# Solo first — the action runs the suite, it does not start a network
- uses: hiero-hackers/hiero-tck-action@<commit sha>
  with:
    startServer: false            # the workflow builds and backgrounds our server
    rpcServerPort: 8544
    tckTag: v0.13.0             # the action still defaults to v0.12.4
    mirrornodeRestJavaUrl: http://127.0.0.1:38081
    testMatrix: src/tests/crypto-service/test-account-create-transaction.ts

Its outputs are a better fit for this project than a plain exit code: it separates genuineFailures from infraFailures and lists unimplementedMethods — which is exactly the shape of our eight failures, where an API gap and a broken server would otherwise look the same.

What it does not do. It is a GitHub Action, so it replaces nothing locally — tck/run-tck.sh and the manual clone stay for development. It does not start a network; Solo remains the caller’s job. Its bundled server presets cover the seven v2 SDKs, not this prototype, so the server comes from startServer: false or a dockerfilePath. And it carries no tags or releases yet — pin a commit SHA.

05One createAccount, end to end

The seven hops a single TCK method takes — the path the spike had to make work before any test could turn green.

34 / 42 passing · Java 34 / 42 passing · TypeScript 8 failures, the same set in both

The eight failures are API gaps, not defects: Authority has no toBytes/fromBytes, so key lists and threshold keys cannot be read or written; PublicKey has no EVM address; and a precheck rejection surfaces as an internal error instead of a status. Four problems the spike had to work around are recorded in the ## Questions & Comments of the specs they belong to — a client that cannot reach its own network, a response that cannot query anything, a factory that takes the wrong address type, and a status enum without SUCCESS.

07Running it

JDK 25 comes from .sdkmanrc, Maven from the wrapper — sdk env once per shell, then everything from the repository root.

The generator

# build the CLI
./mvnw -f tooling/metalang/pom.xml verify

# the specs themselves
metalang validate spec

# one language
metalang generate --language=java --config=sdk-java/generator.properties \
         --output=generated/java spec

# does a project still provide the API of the specs?
metalang check --language=java --fail-on=never \
         --config=sdk-java/generator.properties --project=generated/java spec

Protobuf

protobuf/update.sh                  # re-fetch from the pins in sources.json
protobuf/verify.sh                  # compile every root with protoc
npm run gen:proto-ts                # TypeScript messages (buf + protoc-gen-es)

The TCK

solo one-shot single deploy         # a local network

./mvnw -f sdk-java/support install
./mvnw -f sdk-java/protobuf install
./mvnw -f generated/java install -DskipTests
./mvnw -f generated/java-tck/contract install
./mvnw -f tck/runtime/java install
./mvnw -f generated/java-tck/server clean package

TCK_DIR=../hiero-sdk-tck tck/run-tck.sh java \
    src/tests/crypto-service/test-account-create-transaction.ts

And the build-time crossing — how much of the TCK’s own method list the bindings already cover:

metalang tck check --bindings=tck/bindings \
         --tck=../hiero-sdk-tck/docs/test-specifications spec

Two things that cost an hour each. The server needs clean package — an incremental build keeps the previous manifest, so a newly added dependency lands in target/lib but not on the class path. And metalang check needs --fail-on=never, because six pre-existing collection.nullable findings in the specs otherwise stop it before it checks anything.

TCK_SERVER_LOG=debug prints the stack trace of every failed call; at the end of a run the server lists the distinct causes with counts — during the stub phase that list is effectively the backlog of API methods to implement next.
