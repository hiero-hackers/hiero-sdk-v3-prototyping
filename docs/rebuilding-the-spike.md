# The Java implementation (`sdk-java/impl`) and the TypeScript spike

How the V3 API is implemented today, how to build and verify it, and what cost time on the way. Written to be
executed by an agent.

- **Java:** `sdk-java/impl` is a **copy of the generated Java project** that is maintained by hand. All 84 tests of the
  specs pass against it (keys 44, ledger 29, transactions 10).
- **TypeScript:** only the first spike, which was written into the generated code in place and exists in git
  history only (section 6).

Both started as the same vertical slice: the `createAccount` path of the TCK (keys → protobuf → gRPC → signing →
receipt polling). The in-place spike reached 34 of the 42 tests of the TCK's `test-account-create-transaction.ts`
against a local Solo network, in Java and TypeScript, with the same eight failures. Its last state is `3b5305d~1`
(introduced in `3caad63 "Durchstich :)"`). Rust has no slice: `metalang tck generate` supports only
`--language=java|ts`.

## 1. How `sdk-java/impl` came about

The generator produces the API only — every method body it cannot derive is a stub that throws
`UnsupportedOperationException("Not implemented yet: Type.method")`. Generation is an aid to bring the specs
correctly into the API of the SDK, not the SDK itself. So the generated project was copied once and became
hand-written code:

1. `scripts/generate-java.sh` into `sdk-java/generated`.
2. `sdk-java/generated` copied to `sdk-java/impl` (without `target/`): the parent `pom.xml` and the five modules, with
   the **same Maven coordinates and JPMS modules** — `impl` is the SDK, `generated` only the reference.
3. In every file removed: the header line `// Generated by metalang …` (`<!-- … -->` in the POMs),
   `@Generated(…)` / `@javax.annotation.processing.Generated(…)`, `import javax.annotation.processing.Generated;` and
   `requires static transitive java.compiler;`.
4. The generated tests came along: the contract tests per type (`<Type>Test`) and the tests of the specs
   (`<Spec>SpecTest`).

From then on, `impl` is edited like any hand-written code: stub bodies are filled in place, helpers go into
non-exported `internal` packages, dependencies are added to the module POMs and `module-info.java`.

**Open: how later spec changes reach `impl`.** Today: regenerate into `sdk-java/generated`, compare, carry the
changes over by hand. `metalang check --project=sdk-java/impl` reports where `impl` no longer provides the API of the
specs (it allows filled bodies and additional types). Whether this needs tool support (e.g. a three-way merge from the
last copied generation) is not decided.

`HapiTransactionStatus` is mechanical — regenerate it instead of editing it:

```bash
python3 - <<'PY'
import re
src = open('tooling/protobuf/consensus-node/services/response_code.proto').read()
body = src[src.index('enum ResponseCodeEnum'):]; body = body[:body.index('\n}')]
seen, out = set(), []
for name, num in re.findall(r'^\s*([A-Z][A-Z0-9_]*)\s*=\s*(\d+)\s*;', body, re.M):
    if name not in seen: seen.add(name); out.append((name, int(num)))
print(len(out), 'constants, SUCCESS =', dict(out)['SUCCESS'])
PY
```

**Implementing another transaction type:** add a `TransactionKind` to `TransactionKinds` (gRPC service and method,
body field, receipt) and let the nine methods of the type delegate to `new Packing<>(TransactionKinds.X)`, as
`PrngTransaction` does.

## 3. Build and verify

In `sdk-java` (JDK 25, `sdk env`):

```bash
./mvnw -f support install
./mvnw -f test-support install
./mvnw -f protobuf install
./mvnw -f impl install -Dmaven.test.failure.ignore=true
```

**Done when:**

- `KeysSpecTest` 44/44 and `LedgerSpecTest` 30/30 (`org.hiero.base`) and `TransactionsSpecTest` 10/10
  (`org.hiero.consensus.node.client`) pass. The contract tests of methods nobody has implemented yet fail by design,
  hence `-Dmaven.test.failure.ignore=true`;
- the conformance check still reports *provides the API of the specs*:

  ```bash
  java -jar tooling/metalang/target/metalang-*-cli.jar check --language=java --fail-on=never \
       --config=sdk-java/generator.properties --project=sdk-java/impl spec
  ```

**The TCK** needs a local Solo network (`solo one-shot single deploy`, i.e. a running Docker) and a clone of
`hiero-sdk-tck`. `scripts/tck-java.sh` installs `sdk-java/impl` after the generated modules, so the server runs
against the implementation:

```bash
TCK_DIR=../hiero-sdk-tck scripts/tck-java.sh src/tests/crypto-service/test-account-create-transaction.ts
```

The implementation has not been measured against Solo yet. Offline, the server can be checked with a call that
needs no network:

```bash
java -jar sdk-java/tck/generated/server/target/hiero-sdk-tck-*.jar 8599 &
curl -s -X POST -d '{"jsonrpc":"2.0","id":1,"method":"generateKey","params":{"type":"ed25519PrivateKey"}}' \
     http://127.0.0.1:8599/
```

`TCK_SERVER_LOG=debug` prints the stack trace of every failed call.

## 4. Generated tests are fixed at the source, not in `impl`

The tests in `impl` are copies of generated tests. When one of them fails for an implemented method because its
values make no sense (e.g. `"value"` as hex text), the fix belongs in the spec or the generator - a fix in `impl`
alone is undone by the next copy. The first round of this:

| Failure | Fixed by |
|---|---|
| `decode` of `KeyEncoding`/`KeyFormat`/`ByteImportEncoding` with arbitrary text, `PackedTransaction.fromBytes` with random bytes | `@@throws(illegal-format)` in the spec: the generated test accepts the declared error |
| `PrivateKey.sign`/`createPublicKey` on 3 bytes as Ed25519 key | the generator calls methods on the default instance of the type (`defaultSubject()`) when it has one, not on the constructor values of `create()` |
| `AuthorityFactory.of(Integer.MIN_VALUE, …)` | `@@min(1)` on the `threshold` parameter |
| a `ContractId` with neither number nor EVM address as authority | default instances for `ContractId` and `Authority` |
| the sample client submitting to a Hedera testnet node | the default network, consensus node and mirror node of `ledger.md` are those of a local Solo network |

How the change reached `impl` (the update path is still open, see section 1): regenerate into a scratch directory,
`diff -u` the previous generation against the new one, `patch` the main sources of `impl` (only Javadoc changed, the
filled bodies stayed), and replace the changed test files by the new ones without header and `@Generated`. Afterwards
every test file in `impl` equals its generated counterpart.

What is still open: the upper bound of `threshold` (at most the number of children) cannot be expressed in the
meta-language, so `impl` checks only the lower bound - recorded in the `## Questions & Comments` of `authority.md`.

## 5. Traps

These cost time. Each is a real failure that was observed, not a precaution. 12 changed with the copy, 15–17
are new.

1. **`KeysFactory.createPrivateKey` must throw `IllegalArgumentException`** when the bytes are not
   PKCS#8. `JavaConverters.key()` catches exactly that to fall back to the public-key branch; any
   other exception makes a public key unparseable and every `createAccount` fails.
2. **The receipt status must report `code() == 22`.** `JavaTckRuntime` compares against a hard-coded
   `SUCCESS = 22` because `BasicTransactionStatus` has no such constant. `statusJson` uses
   `Enum.name()`, so the status must be an enum whose names match HAPI — hence `HapiTransactionStatus`.
3. **`AccountCreateReceipt` null-checks `exchangeRate` and `nextExchangeRate`.** `queryReceipt()` has
   to supply real values; `null` throws inside the constructor.
4. **`HieroClient` cannot reach its network.** It is a record of operator, `Network` and signer, and
   `Network` carries no `ConsensusNode`. The `NetworkSetting` arrives at `ClientFactory` and ends
   there. Bridge: a registry in `ClientRuntime` keyed by the client instance.
5. **`Response` cannot query anything.** It is a record holding only a `TransactionId`. Bridge: a
   second registry `TransactionId → ClientRuntime`, filled on submit.
6. **`TransactionId.generateTransactionId` takes an `Address`**, but `TransactionId` holds an
   `AccountId` — convert shard/realm/num.
7. **Back-date the valid start by ~10 s** and keep it strictly increasing per process, otherwise the
   node answers `INVALID_TRANSACTION_START`.
8. **Use `Transaction.signedTransactionBytes`**, not `bodyBytes` + `sigMap`: those fields are
   `[deprecated = true]` in the proto and `-Xlint:all -Werror` turns their builders into errors. The
   signed bytes are the serialized `TransactionBody` in both forms.
9. **Set the defaults HAPI requires** — the TCK sends only what a test needs. Without them a bare
   `createAccount` is rejected: `transactionFee` 2 ℏ, `autoRenewPeriod` 90 days,
   `transactionValidDuration` 120 s.
10. **Poll the receipt.** One query is almost always too early. Retry on `UNKNOWN`,
    `RECEIPT_NOT_FOUND`, `BUSY`, `PLATFORM_NOT_ACTIVE` until a timeout, and check the precheck code of
    the `TransactionResponse` before polling at all.
11. **`sdk-java/tck/generated/server` needs `clean package`.** An incremental `package` keeps the
    `Class-Path` of the previous manifest: a newly added dependency lands in `target/lib` but not on
    the class path, and the server dies with `NoClassDefFoundError`.
12. **`internal` packages stay unexported.** `org.hiero.base` does not export its `internal` packages, so the
    client module cannot use `DefaultTransactionId`: it builds transaction ids through the public API
    (`TransactionId.generateTransactionId`, `TransactionId.fromString`) and has its own `DefaultExchangeRate`. A
    qualified `exports … to <module>` would warn that the target is not in the graph — an error under `-Werror`.
13. **gRPC is an automatic module.** `module-info.java` of the client module needs
    `@SuppressWarnings("requires-automatic")`, again because of `-Werror`.
14. **Javadoc is checked.** `-Xlint:all -Werror` plus doclint `all,-missing` with `failOnWarnings`:
    every new type and method needs well-formed documentation, including in non-exported packages.
15. **Same Maven coordinates as `generated`.** Whichever of the two was installed last is what `~/.m2` holds.
    `scripts/generate-java.sh` installs the stubs; run `./mvnw -f impl install` afterwards before building anything
    against the SDK (the TCK script does it).
16. **The byte form of a packed transaction is `TransactionList`** (`sdk/transaction_list.proto`, Java package
    `com.hedera.hashgraph.sdk.proto`), which all SDKs write — the 2125 fixture of `transactions.md` is one. The
    protobuf module exports that package only to the client module.
17. **`seconds.nanos` of a transaction id is an integer number of nanoseconds**, not a decimal fraction
    (`…@1641088801.2` is 2 ns), as in all Hiero SDKs.

## 6. TypeScript: the in-place spike

TypeScript has no `impl` yet. Its slice was written into the method bodies of `sdk-ts/generated` and exists only in
git history; extract it into a scratch directory (`git archive 3b5305d~1 sdk-ts/generated | tar -x -C <scratch>`)
and port it the way the Java one was: copy the generated packages to an `impl`, then fill the stubs there.

The same slice, the same result (34 of 42), and the same eight failures. What differs:

**It is easier.** The abstractions the Java generator turns into `final` classes with static factories are
**interfaces** in TypeScript — `Transaction`, `PackedTransaction`, `TransactionId`, `ExchangeRate`, `Receipt`. The
slice implements them with plain classes in `src/internal/`; nothing has to be squeezed into a generated class.

**The hand-written files**

| File | Responsibility |
|---|---|
| `packages/base/src/internal/der.ts` | the small part of DER the key formats need, plus the three OIDs |
| `packages/base/src/internal/keys.ts` | Ed25519 and ECDSA secp256k1 over `@noble/curves`, PKCS#8/SPKI |
| `packages/base/src/internal/pem.ts` | PEM envelope ↔ DER |
| `packages/base/src/internal/ledger.ts` | `DefaultTransactionId` |
| `packages/consensus-node-client/src/internal/protobuf.ts` | API types ↔ HAPI messages (`@bufbuild/tooling/protobuf`) |
| `packages/consensus-node-client/src/internal/client.ts` | `ClientRuntime`: gRPC, node selection, submit, receipt polling, the registries |
| `packages/consensus-node-client/src/internal/packed.ts` | `DefaultPackedTransaction` |
| `.../consensusnode/transactions/HapiTransactionStatus.ts` | one constant per `ResponseCodeEnum` value |

**The filled stubs** are the same set as in Java: the key enums and factory functions, `PrivateKey`/`PublicKey`,
`AccountId`, `IpAddress`, `Hbar`, `TransactionId.generateTransactionId`, `authority.of*`, `createClient`,
`Response.queryReceipt`, `AccountCreateTransaction.signWithOperator`.

**Dependencies** (in the repository-root `package.json`, which is hand-written): `@noble/curves`, `@noble/hashes`
and `@grpc/grpc-js`. The protobuf runtime `@bufbuild/tooling/protobuf` is already wired by the generator (`ts.protobuf`).

**Build and verify**

```bash
npm --prefix sdk-ts install && npm --prefix sdk-ts run gen:proto-ts
npm run build:tck-ts
TCK_DIR=../hiero-sdk-tck tck/run-tck.sh ts src/tests/crypto-service/test-account-create-transaction.ts
```

### TypeScript traps

These replace or add to section 5; the numbers are independent.

1. **The fallback catches `RangeError`, not `Error`.** `TsConverters.key()` of the TCK runtime falls back from
   private to public key on `RangeError` — so every failure in the key code must be a `RangeError`. This is the
   TypeScript counterpart of Java's `IllegalArgumentException` and the single most important rule here.
2. **`statusJson` reads `value.name`.** The status has to be a generated-style enum class with a `name` getter, not
   a plain object — hence `HapiTransactionStatus` as a class with static instances.
3. **Generated constructors call `Object.freeze(this)`.** A subclass of `PrivateKey` or `PublicKey` cannot add
   instance fields. The slice therefore implements the bodies *in* those classes, switching on `algorithm`, instead
   of subclassing as the Java slice does.
4. **`TransactionSigner` is an interface with `signTransaction(bytes, node)`**, not a function type. Pass an object,
   and call `client.transactionSigner.signTransaction(...)`.
5. **The client package cannot import `@hiero/base/internal/…`.** That is the point of the `exports` map — and it
   holds inside the repository too. The client gets its `TransactionId` from the public
   `TransactionId.generateTransactionId(new Address({...}))` and defines its own `ExchangeRate` value, because
   `ExchangeRate` is an interface.
6. **Strict compiler options bite.** `noUncheckedIndexedAccess` makes every array access `T | undefined`, and
   `noUnusedLocals` rejects an import that a file does not use. Both are errors, not warnings.
7. **protobuf-es rejects out-of-range values before the network does.** A negative `initialBalance` fails with
   `invalid uint64: -1` instead of reaching the node — where Java gets `INVALID_INITIAL_BALANCE` back. Both fail
   that test, for different reasons.
8. **`@noble/curves` v2 needs the `.js` subpath** (`@noble/curves/secp256k1.js`) and returns the ECDSA signature
   already as the 64 bytes `r‖s`.

## 7. What it is not

The registries of traps 4 and 5 are workarounds for spec problems recorded in the `## Questions & Comments` of
`spec/consensus-node-client/client.md` and `transactions.md`, not a design. Most of the API is still a stub: only
`PrngTransaction` and `AccountCreateTransaction` of the transaction types, no queries, no mirror node client, no
`Response.queryRecord`.

The 8 failing TCK tests of the spike are API gaps, not bugs: `Authority` has no `toBytes`/`fromBytes` (key lists,
threshold keys), `PublicKey` has no EVM address, and a precheck rejection surfaces as `-32603` instead of `-32001`
with a status.
