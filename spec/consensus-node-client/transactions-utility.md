# Utility Transactions API

This namespace groups utility transactions of the consensus node's *util* service — transactions
that do not belong to a specific entity service (accounts, tokens, topics, files, schedules) but
provide cross-cutting platform utilities. The first such transaction is `PrngTransaction`
(HIP-351), which asks the network for a verifiable pseudorandom value.

## Description

### `PrngTransaction` (HIP-351)

`PrngTransaction` requests a pseudorandom value derived from the network's running hash. The
randomness is generated by consensus — every node computes the same value from the same
deterministic seed — so the result is **verifiable** and not controllable by any single party
(including the submitter). The value is produced during transaction handling and is part of the
record of the transaction: read the receipt with `Response.queryRecord()` (its `receipt`), not with
`Response.queryReceipt()`, whose answer from the network does not contain the value.

The payload is a single optional `range`:

- **`range` unset** → the receipt carries `prngBytes`: 384 bits (48 bytes) of pseudorandom data.
- **`range` set** (must be `> 0`) → the receipt carries `prngNumber`: a pseudorandom 32-bit integer
  uniformly distributed in the half-open interval `[0, range)`.

In a receipt read from the record, exactly one of the two fields of `PrngReceipt` is populated,
mirroring which input mode was chosen; in a receipt from `queryReceipt()` both are absent. The
transaction changes no ledger state beyond charging the fee — its sole observable effect is the value
in its record.

## Design Notes

- HAPI returns the random value only in the `TransactionRecord` (`prng_bytes` / `prng_number`, HIP-351);
  the `TransactionReceipt` has no such field. The receipt the SDK builds from a record carries it, the
  one of a receipt query cannot. So the rule "at most one receipt field" is `@@oneOrNoneOf(prngNumber,
  prngBytes)` on `PrngReceipt`, not `@@oneOf`.

## API Schema

```
namespace consensusnode.transactions.utility
requires {Receipt, Transaction} from consensusnode.transactions

// Requests a verifiable pseudorandom value from the network (HIP-351). The randomness is derived
// from the consensus running hash, so the result cannot be steered by the submitter.
//
//   - range unset      → the receipt carries prngBytes (384 bits / 48 bytes of randomness)
//   - range set (> 0)  → the receipt carries prngNumber, uniform in [0, range)
@@finalType
PrngTransaction extends Transaction<PrngReceipt, PrngTransaction> {
    @@immutable @@nullable @@min(1) range: int32   // unset → 384 random bits; set → a random int in [0, range)
}

// Carries the generated pseudorandom value. In the receipt of the record (Response.queryRecord) exactly one field
// is set, matching the input mode of the PrngTransaction that produced it; the receipt of Response.queryReceipt has
// neither, as the network returns the value only in the record.
@@oneOrNoneOf(prngNumber, prngBytes)
@@finalType
PrngReceipt extends Receipt {
    @@immutable @@nullable prngNumber: int32   // set when range was provided; uniform in [0, range)
    @@immutable @@nullable prngBytes: bytes    // set when range was unset; 384 bits (48 bytes) of randomness
}
```

## Examples

### Request a random number in a bounded range

A lottery picks a winning ticket out of 10 000 sold. Supplying `range` makes the network return a
number in `[0, 10000)` directly.

```
HieroClient client = ...;

PrngReceipt receipt = new PrngTransaction()
    .range(10000)
    .signWithOperatorAndSubmit(client)
    .queryRecord()
    .receipt;

int32 winningTicket = receipt.prngNumber;   // 0 .. 9999
```

### Request raw random bytes

Without `range`, the receipt of the record yields 48 bytes of randomness — e.g. to seed a
client-side generator or derive a nonce.

```
PrngReceipt receipt = new PrngTransaction()
    .signWithOperatorAndSubmit(client)
    .queryRecord()
    .receipt;

bytes seed = receipt.prngBytes;   // 48 bytes
```

## Testing

Offline tests of `PrngTransaction`, written as given / when / then: the attributes it keeps, its packed form and the range it rejects. The
random value itself is produced by the network and is tested by the TCK, not here.

```tests
// Source: this spec (range is @@nullable); the Python SDK (test_constructor_default_values).
test "a PRNG transaction without a range asks for random bytes" {
    // when
    let transaction = PrngTransaction{}

    // then
    assertNull(actual: transaction.range)
}

// Source: the Python SDK (test_constructor_with_parameters, range 1000) and the Go SDK (TestUnitPrngTransactionSetRange).
test "a PRNG transaction keeps its range" {
    // when
    let transaction = PrngTransaction{range: 1000}

    // then
    assertEquals(expected: 1000, actual: transaction.range)
}

// Source: the JavaScript SDK ("should return range when create transaction from Bytes", range 100) and the Go SDK
// (TestUnitPrngTransactionFromToBytes).
test "a PRNG transaction with a range survives toBytes and fromBytes" {
    // given
    let packed = PrngTransaction{range: 100}
            .pack(payer: DEFAULT(consensusnode.client.Account), nodes: [ledger.AccountId.fromString(value: "0.0.3")])
    let bytes = packed.toBytes()

    // when
    let restored = consensusnode.transactions.PackedTransaction.fromBytes(bytes: bytes)

    // then
    assertEquals(expected: bytes, actual: restored.toBytes())
    assertEquals(expected: packed.signableBodies(), actual: restored.signableBodies())
}

// Source: this spec (@@min(1)); the Python SDK rejects a negative range
// (test_build_proto_body_with_negative_range_raises_error).
test "a PRNG transaction rejects a range of 0" {
    // when / then
    @@expectThrows(invalid-argument-error)
    PrngTransaction{range: 0}
}
```

## Questions & Comments

- **`prngNumber` is a signed `int32`, but the value is always non-negative.** HAPI returns the
  bounded result as an `int32` in `[0, range)`; `range` itself is a positive `int32`, so the result
  never overflows into the sign bit for any `range`. The field is left as `int32` (rather than an
  unsigned type the meta-language does not have) to match HAPI exactly; the `[0, range)` contract is
  documented on the field.

- **No client-side validation that the network supports HIP-351.** A ledger whose consensus node
  does not implement the util service rejects the transaction with a `TransactionStatus` on the
  receipt, consistent with how every other service-specific transaction surfaces unsupported
  operations (see [`transactions-schedule.md`](transactions-schedule.md) for the same reasoning
  about schedulable inner transactions).

- **Why a transaction and not a query.** The value is produced *during* consensus handling and
  recorded in the record of the transaction; it cannot be read back without changing the network's running-hash
  state.
  Modelling it as a `Transaction<PrngReceipt, PrngTransaction>` keeps it on the existing receipt-per-transaction
  pattern (see [`missing-features.md`](../../docs/missing-features.md) §3.5) rather than inventing a
  side-effecting query.
